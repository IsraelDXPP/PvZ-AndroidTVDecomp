# Agent rules for LawnTVDecomp

Rules for any agent (Claude Code, opencode, Codex, ...) working in this
repository. Each one exists because something went wrong, or was about to go
wrong, on a real task. They are not style preferences.

`CLAUDE.md` is the project orientation and the map of the documentation.
Read it first; this file is the short list of things that must not be broken.

## 1. The binary decides, and the binary is a specific build

The source of truth is the **v115** build of `libGameMain.so` from the TV /
Android edition:

```text
https://github.com/ZombieYetis/PlantsVsZombies-AndroidTV
  app/src/v115/jniLibs/armeabi-v7a/libGameMain.so
```

Everything in the port follows that binary: function names, field layouts,
constants, control flow, and the addresses quoted in the comments.

- Never port from PC PvZ, from the HD edition, or from "what the game should
  do". The TV build differs.
- Every change carries the address it came from, in the existing format:

  ```cpp
  // ==========================================================================
  // LawnApp::HasSeedType(SeedType,bool)
  // @002B756C  238 bytes
  // ==========================================================================
  ```

  The banner is `// Class::Method(Args)`, then `// @00XXXXXX  N bytes`, where
  the size is the function size in the v115 symbol table. Inline notes use
  `// @0x2B756C: ...`.
- If you cannot find the function or you do not understand the pseudo-C, write
  no code. Leave `// NOT IN BINARY: <what is missing>` and say so in your
  answer.
- Never write "measured" or "verified" without saying how: the address, or
  the command you ran.

## 2. There are two builds, and only one of them matches the citations

`v115` (6,936,968 bytes) and `w111` (6,923,240 bytes) are two different
builds of the same library. The addresses quoted in this repository belong to
**v115**.

The Hex-Rays export kept on this machine,
`C:\Users\nydil\Documents\libGameMain.so.c`, is the **w111** build
(`LawnApp::HasSeedType` is at `0x2B49A8` there, not `0x2B756C`). The older
export under `Documents\antigravity\optimistic-lovelace\pseudocode\` is a third
build.

Consequences:

- An address mismatch against a local export is **not** evidence that the code
  in this repository is wrong. Match by function name and by behaviour.
- Never "correct" an address quoted in the code using a local export. The
  quote is the authority.
- Use the symbol table of the v115 `.so` as the tie breaker:

  ```sh
  nm -C -D --defined-only -S libGameMain.so | grep ShowHouseScreen
  ```

  Thumb symbols carry the low bit: `0x2b344d` means the function is at
  `0x2B344C`. `docs/binario.md` has the full fingerprint table.

## 3. Do not add what the binary does not do

No extra null checks, no extra calls, no "safety" branches, no extra drawing,
no `AddWidget` that the binary does not do. If the port crashes, the cause is
almost always a missing image, a missing resource, or a wrong offset: find it,
do not paper over it.

If the binary *does* do something (a `+ 6`, a `* 0.5`, a `SetLinearBlend`),
copy it exactly. Compare the port function with the pseudo-C line by line
before you finish.

## 4. Never write numbers by hand

Seed types, plant types, store items, reanimation ids, image ids, game modes:
use the enums. They live in `Sexy/include/ReconTypes.h`
(`SEED_*`, `STORE_ITEM_*`, `REANIM_*`, `GAMEMODE_*`).

```cpp
// Wrong: a literal that silently rots when the table changes.
if (mPurchases[4] > 0) ...

// Right:
if (mPurchases[STORE_ITEM_PLANT_GATLINGPEA] > 0) ...
```

## 5. The machine-transcribed files are not yours to edit

Forty-six sources and three headers carry the banner
`Generated by tools/ida_transcribe.py. Do not edit.`:

- `Lawn/src/game/`: `Attachment`, `Board`, `Challenge`,
  `ConfirmBackToMainDialog`, `CreditsOverlay`, `CutScene`, `DataWriter`,
  `GameCenter`, `GamepadControls`, `HelpOptionsDialog`, `internalJSONNode`,
  `JSONWorker`, `LawnMenuParser`, `LawnSession`, `LawnStoneButton`,
  `LawnUser`, `LevelStats`, `LogComposer`, `MainMenu`, `MaskHelpWidget`,
  `Music2`, `NativeApp`, `NotificationManager`, `ParseWidget`, `Plant`,
  `ReanimationButton`, `ReanimatorDefinition`, `ReanimatorTransform`,
  `SaveGameContext`, `SeedChooserScreen`, `ShareManager`, `StartButton`,
  `StretchableGameButton`, `TestMenuWidget`, `TitleScreen`,
  `TreeOfWisdomControls`, `VSSetupMenu`, `Zombie`.
- `Sexy/src/`: `ButtonListener`, `InputDriverFactory`, `PIEmitter`,
  `PITexture`, `PlayerInfo`, `SingleDataElement`, `XMLWriter`.
- `TodLib/src/`: `SyncObject`.
- `Sexy/include/`: `ReconData.h`, `ReconFreeFunctions.h`, `ReconTypes.h`.

`Sexy/src/ReconImageIds.cpp` is generated too, by `tools/gen-image-ids.py`,
and says so in its own banner. The rest of the `Recon*` family
(`ReconExterns.h`, `ReconHelpers.h`, `ReconData.cpp`, `ReconFuncs.cpp`,
`ReconGlobals.cpp`, `ReconHelpers.cpp`, `ReconStatics.cpp`, `ReconStubs.cpp`,
`ReconSubsLow.cpp`, `ReconSubsMisc.cpp`, `ReconSubsString.cpp`,
`ReconSubsVector.cpp`, `ReconVariadic.cpp`) is hand written.

Neither generator is in this repository. Before you touch one of those files,
find the generator. If it cannot be found, do not rewrite the file: make the
smallest possible change, keep the banner, and record the change in
`docs/estado.md`.

The same applies to the console content adapted from
`PlantsVsZombies-AndroidTV`: it is GPL-3.0-or-later, it keeps its header, and
`ThirdParty/PvZTVTouch/NOTICE.md` must stay in sync with it.

## 6. The fork must stay mergeable with the upstream

The upstream is `https://cnb.cool/wanxiace/LawnTVDecomp` (remote `origin`).
A scheduled job merges it into a branch and opens a pull request into `main`.
See `docs/upstream.md`.

- Prefer additive changes in separate files. Do not reformat, re-indent or
  "modernise" a file you are not fixing: the next upstream merge will
  conflict on every line.
- Run `git diff origin/main..main --stat` before committing and look at what
  is ours. If a diff is unrelated to the change you are making, it is not
  yours to keep.
- Never let the upstream's `.github/workflows` replace the fork's; the sync
  job restores them, but do not rely on it.

## 7. Hex-Rays traps

- `a1` is `this`. `*(LawnApp **)(a1 + 776)` is the field at offset 776, which
  is `*((LawnApp **)this + 194)`. The port has real fields: use the field, not
  the offset.
- `sub_XXXXXX` and `dword_XXXXXX` are not names. Find the real name in the
  symbol table, in a header, or in the `Recon*` layer.
- `__fastcall`, `_DWORD`, `_BOOL4`, `JUMPOUT(0)` and `// idb` are decompiler
  artefacts, not code.
- `LODWORD` / `COERCE_FLOAT` are the same value mistyped. Look at the asm.
- Unsigned comparisons: `(unsigned)(x - 19) <= 1` is `x == 19 || x == 20`.
  Keep the shape.
- No pointer arithmetic tricks (`sizeof(Zombie)`, subtracting addresses to
  recover an id). They break on 64-bit targets.

## 8. Do not delete the marks

`// NOT IN BINARY: ...` and `// UNVERIFIED: ...` stay until the code does
exactly what the binary does, and the comment says where that was checked.

Never delete a `// @00XXXXXX  N bytes` banner because the body was edited.
Update the size when the binary's function is different, and say so.

## 9. English everywhere in the code and the docs

The README requires it: all project documentation, comments, configuration
descriptions, diagnostics and built-in fallback text are in English. Identifiers
are English too. Conversation with the user may be in any language; the
repository is not.

## 10. Build and verify before you commit

```powershell
cmake --fresh --preset windows-x64-release
cmake --build --preset windows-x64-release --parallel
build\windows-x64-release\bin\Release\LawnTV.exe --frames 5 --screenshot smoke.png --headless
```

The smoke test must exit with code 0 and write a 1280x720 PNG. The exact
commands, and what counts as verified, are in `docs/verificacion.md`.

Do not say "it works" if you did not run it, and do not say "the build
passes" if you only built one file. There is no test suite in this project:
the build plus the smoke test plus reading the diagnostics log is the
verification.

## 11. Style

- Four spaces, no tabs, Allman braces, 120 columns (`.clang-format`).
- `clang-format -i <file>` on the files you touched. Do not run it on files
  you did not touch: it produces a diff the upstream merge will fight over.
- One topic per commit. The message says what changed, in which function, and
  the address. The history is in English and imperative; follow it.
- Do not commit binaries, assets, `build/`, `vcpkg_installed/`, IDA databases
  or the `.pak` files. They are ignored; keep it that way.

## Checklist before every commit

1. Does every changed function carry the `@00XXXXXX` address of the v115
   build, and did you compare it with the pseudo-C line by line?
2. Is every number an enum or a named constant, not a literal you typed?
3. Did you touch a generated file? If yes, is the generator accounted for?
4. Does `git diff` contain only what this change needs? No reformatting, no
   drive-by fixes.
5. Does `git diff origin/main..main --stat` still show only the intended fork
   changes?
6. Did the build and the smoke test run, with the exact output recorded?
7. Is the unverified part marked as such, and `docs/estado.md` updated?
