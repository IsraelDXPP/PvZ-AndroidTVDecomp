# Method

How a function travels from the binary into this repository, and what to do
at every step. The method exists because the project is a decompilation: the
port is only correct when it matches the binary, and "it looks right" is not
a reason.

## Order of confidence

When two sources disagree, the higher one wins:

1. **The v115 symbol table** (`nm -C -D --defined-only -S`): names, addresses
   and function sizes. Never wrong.
2. **The IDA database and its Hex-Rays output** of the v115 build: the
   control flow, the offsets, the constants.
3. **The port itself**, as it is today: a hypothesis, until the binary
   confirms it.
4. **The upstream project** (`cnb.cool/wanxiace/LawnTVDecomp`): another
   engineer's reading of the same binary. Useful as a second opinion, never
   as the authority.
5. **PC PvZ, the HD edition, the console release, the Wiki**: context only.
   They are a different game with different data.

## Taking one function

### 1. Find it by name

```sh
nm -C -D --defined-only -S libGameMain.so | grep 'HasSeedType'
```

The name gives the address, the size and the signature. The `Class::Method`
banner in the code comes from here.

### 2. Read it

Open the function in IDA (the database is described in `docs/binario.md`), or
find the same body in the Hex-Rays export. The export is greppable by name;
the address in the export belongs to another build, so the name is the key
and the address is not.

### 3. Compare line by line

Read the port function and the pseudo-C side by side. For each statement in
the pseudo-C there must be a statement in the port, and nothing in the port
that is not in the pseudo-C. Differences fall into three buckets:

- **The port is wrong.** Fix it. This is the normal case.
- **The pseudo-C is ambiguous** and the port made a choice. That choice must
  be visible in a comment, with the address.
- **The port does something the binary does not** (a null check, a call, a
  draw). It came from somewhere else: find out where, and remove it or
  justify it.

### 4. Cite the address

```cpp
// ==========================================================================
// LawnApp::HasSeedType(SeedType,bool)
// @002B756C  238 bytes
// ==========================================================================
```

- The banner is the demangled signature, exactly as `nm -C` prints it.
- `@00XXXXXX` is the address from the v115 symbol table, eight uppercase hex
  digits.
- `N bytes` is the size from the same table. When the size in the banner and
  the size in the table differ, the table wins and the banner is corrected
  (there is one known case: `LawnApp::SaveFileExists`, 136 bytes in the table
  and 112 in the banner).
- Inline notes quote the address of the statement they talk about:
  `// @0x2B756C: these reads are the nine plant purchase slots ...`.

The banner goes above the function it describes. A banner is never removed:
it is the only record of where the body came from.

### 5. Use names, not numbers

`SEED_*`, `STORE_ITEM_*`, `REANIM_*`, `GAMEMODE_*` and the rest live in
`Sexy/include/ReconTypes.h`. The tables in the binary are the source of those
enums; a literal typed by hand rots the moment the table changes.

Field access is a named field, never an offset. The port keeps the binary's
layout in the headers, so `mPurchases[STORE_ITEM_PLANT_GATLINGPEA]` is both
readable and checkable against the pseudo-C's `+ 776` style access.

### 6. Mark what is not verified

Two markers, both in English, both kept until they can be removed with a
measured reason:

```cpp
// NOT IN BINARY: <what the original did instead, and why this exists>
// UNVERIFIED: <the part that was not checked against the binary, and what
//              would settle it>
```

`NOT IN BINARY` is for the code that the TV build does not have: the restored
console content, the SDL3 and bgfx platform layer, the PC-style options behind
`setup.env`. `UNVERIFIED` is for a ported function whose binary counterpart
was not read closely enough.

Both markers say what is missing. A marker without a "what would settle it"
is not a marker, it is a shrug.

## The machine-transcribed files

Forty-six sources and three headers (`Sexy/include/ReconData.h`,
`ReconFreeFunctions.h`, `ReconTypes.h`) are machine-transcribed from IDA by
`tools/ida_transcribe.py` and carry the banner `Do not edit.`
`Sexy/src/ReconImageIds.cpp` is generated by `tools/gen-image-ids.py` and
says so in its own banner. Neither generator is in this repository, and
neither is in the upstream either.

That means:

- Do not hand-edit them to "fix" a function. A hand edit is lost the next
  time the file is transcribed.
- If a fix is unavoidable, make it the smallest possible change, keep the
  banner, and record it in `docs/estado.md` so the next transcription does
  not silently drop it.
- The `Recon*` headers are the shared declarations of the transcribed layer.
  They are the first place to look for the real name of a type, and the enum
  tables live there. The hand-written part of the family
  (`ReconExterns.h`, `ReconHelpers.h` and the `Sexy/src/Recon*.cpp` files
  other than `ReconImageIds.cpp`) is where the recovered helpers live.

The console content adapted from `PlantsVsZombies-AndroidTV` is not machine
transcribed, but it is GPL-3.0-or-later: it keeps its copyright header, and
`ThirdParty/PvZTVTouch/NOTICE.md` has to stay in sync with it.

## Working in this fork

This repository is a fork with an upstream that pushes into it. The method
above applies to the game logic; the packaging, the CI and the platform layer
follow the fork's own conventions.

- Keep the ported code and the restored code apart: restored code lives in
  its own files with its own header, and it is the one the upstream also
  carries. Do not mix the two inside one function.
- When the upstream changes a function that was ported here, re-read the
  binary for that function and update the port. The upstream's version is
  not automatically right.

## Reading the Hex-Rays export without being misled by it

- `a1` is `this`, and the offsets in the export are absolute from the object
  start: `*(LawnApp **)(a1 + 776)` is field 194 of the class, at byte 776.
- The export's addresses are from another build. Use the name.
- `JUMPOUT(0)` and `// control flows out of bounds` mean Hex-Rays gave up.
  Read the asm in IDA; do not guess the intent.
- `_DWORD` is an `int` in the port, `__fastcall` disappears, `// idb` means
  the name came from the database.
